# 医疗系统数据库设计与增量迁移

本次在现有科室、医生、患者、挂号四张表上增量扩展，为实验二CRUD和实验三排班、挂号、处方、库存事务准备数据库基础。已有记录不删除、不重建、不自动重写。

执行状态以本机 .local/database-design/execution-status.json 和本目录的“数据库增量迁移验证结果.json”为准：只有 success / APPLIED 且验证通过才能视为落库完成。设计文档存在不代表数据库已变更。

执行前核对：MySQL 8.0.45，medical_system 有4个科室，医生、患者、挂号均为空。此前自己增加的科室也在保护范围内。备份、数据比对快照及执行状态保存在项目 .local 私有目录，不提交 Git 或源码包。

共10张业务表，另外1张 schema_migration 为技术迁移记录。现有 appointment 在课程中承担“挂号记录”的职责，无需另建语义重复的 registration 表。

课程模型约定：

- 每名医生归属一个当前科室；历史科室调动、批次药品、多库房管理暂不实现。
- 一名医生在一天的一个标准时段只能有一个排班；同一天时段不重叠需应用层进一步校验。
- 一次挂号至多一张处方，处方包含多条药品明细。草稿阶段可暂时没有明细，开立时业务层须保证至少一条。
- 药品库存使用整数最小单位，例如盒或片；发药数量与药品单位一致，不能混用盒与片而不换算。
- 处方单价与库存流水余额是业务发生时的历史快照，不能因目录调价或后续出入库而修改。

基础实体和明细分表，避免重复存姓名、科室名称及计算金额。剩余号源、当前库存为需事务维护的业务计数器，流水余额与处方价格为历史快照；这些都必须在报告中说明一致性维护方式。为兼容旧代码保留的挂号医生列例外见下一节，不能笼统声称现有全部表已严格满足第三范式。

## 2. 旧表变更及兼容

| 表 | 处理方式 | 兼容依据 |
| --- | --- | --- |
| department | 不变更字段、不写演示数据 | 保留所有科室和原有CRUD |
| doctor | 新增 doctor_no、phone及索引 | 新字段可空，不为旧记录编造工号 |
| patient | 新增 identity_card及索引 | 新字段可空，多个NULL可共存，非空证件号唯一 |
| appointment | 新增 schedule_id、生成列及约束 | 旧挂号允许无排班；新挂号必须由Service关联排班 |

现有 appointment.doctor_id 为兼容旧代码保留；迁移加入 (schedule_id,doctor_id) → doctor_schedule(id,doctor_id) 复合外键，防止挂号医生与排班医生不一致。该医生列可由排班推导，属于兼容性保留的冗余，不将此部分宣称为严格第三范式；后续完成挂号Service迁移、旧记录排班映射后，可另行评估删除该冗余列。

## 3. 字段说明

说明：PK主键，FK外键，UK唯一；“可空”未标注时均为NOT NULL。所有业务表为 InnoDB / utf8mb4。普通id为BIGINT自增；所有原表原字段与原约束保持原样。

### department 科室

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| code | VARCHAR(32) | UK，科室编码 |
| name | VARCHAR(64) | 科室名称 |
| description | VARCHAR(255) | 可空，简介 |
| created_at | DATETIME | 默认当前时间 |

### doctor 医生

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| department_id | BIGINT | FK → department.id |
| name | VARCHAR(64) | 姓名，索引 |
| title | VARCHAR(64) | 可空，职称 |
| doctor_no | VARCHAR(32) | 新增、可空、UK，医生工号 |
| phone | VARCHAR(32) | 新增、可空，电话 |
| created_at | DATETIME | 默认当前时间 |

### patient 患者

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| name | VARCHAR(64) | 姓名，索引 |
| gender | VARCHAR(16) | 原有可空字段，保留原语义 |
| birth_date | DATE | 可空，生日，不存随时间变化的年龄 |
| phone | VARCHAR(32) | 可空，电话，新增非唯一索引；允许家庭共用电话 |
| identity_card | VARCHAR(18) | 新增、可空、UK；新输入空字符串应规范化为NULL |
| created_at | DATETIME | 默认当前时间 |

手机号、身份证正则及身份证校验位需要后续DTO与Service实现；本次仅提供字段和非空值唯一约束，不把“能存字符串”等同于已完成敏感字段格式校验。接口后续应脱敏、按角色隔离，实验仅用虚构数据。

### doctor_schedule 医生排班

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| doctor_id | BIGINT | FK → doctor.id |
| work_date | DATE | 出诊日期 |
| time_slot | VARCHAR(16) | MORNING / AFTERNOON / EVENING |
| start_time / end_time | TIME | 同日开始<结束，不支持跨日 |
| total_capacity | INT | 总号源≥0 |
| remaining_capacity | INT | 0≤剩余号源≤总号源 |
| status | VARCHAR(16) | OPEN / CLOSED，默认OPEN |
| version | INT | 非负，默认0；应用显式递增 |
| created_at / updated_at | DATETIME | 创建与修改时间 |

UK：(doctor_id,work_date,time_slot)；兼容复合FK需要UK：(id,doctor_id)；检索索引：(work_date,status)。时段重叠、出诊日期不得过期、已挂号后调整容量均属后续Service规则。

### appointment 挂号记录

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| appointment_no | VARCHAR(40) | UK，业务编号 |
| patient_id | BIGINT | FK → patient.id |
| doctor_id | BIGINT | FK → doctor.id，兼容旧实现 |
| appointment_time | DATETIME | 原有就诊时间字段 |
| status | VARCHAR(20) | PENDING / COMPLETED / CANCELLED |
| schedule_id | BIGINT | 新增、可空，历史兼容 |
| active_schedule_id | BIGINT | STORED生成列，有效挂号为schedule_id，取消为NULL；不允许写入 |
| created_at | DATETIME | 创建时间 |

复合FK防止医生错配；UK(patient_id,active_schedule_id)防止同患者在同排班下重复有效挂号。取消记录可保留，取消后可重新挂号。旧记录schedule_id=NULL不受此查重键覆盖，后续应用必须要求新挂号提供排班，不能继续创建无排班新记录。就诊时间必须落在排班日期时段内也由Service校验。

### medicine 药品目录

| 字段 | 类型 | 约束或含义 |

| code | VARCHAR(32) | UK，药品编码 |

### medicine_inventory 药品库存

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| medicine_id | BIGINT | PK兼FK → medicine.id |
| stock_quantity | INT | 当前库存≥0，默认0 |
| warning_quantity | INT | 预警阈值≥0，默认0 |
| version | INT | 乐观锁版本≥0，默认0 |
| updated_at | DATETIME | 最近修改时间 |

药品可以先建目录、后建库存记录；可售药品必须由Service在事务内建立库存。当前只建一个库房维度，库存表不重复药品名称、规格或价格。

### prescription 电子处方

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| prescription_no | VARCHAR(40) | UK，处方编号 |
| appointment_id | BIGINT | FK兼UK → appointment.id |
| diagnosis | VARCHAR(500) | 可空，诊断摘要 |
| status | VARCHAR(16) | DRAFT / ISSUED / CANCELLED |
| issued_at | DATETIME | 可空，ISSUED时必须有值 |
| created_at / updated_at | DATETIME | 创建与修改时间 |

不重复保存患者ID、医生ID、姓名或汇总金额；患者与医生通过挂号查得，金额由明细数量×历史单价汇总。诊断字段存储不代表本次已实现诊疗业务或权限控制。

### prescription_item 处方明细

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| prescription_id | BIGINT | FK → prescription.id |
| line_no | SMALLINT | 处方内行号>0 |
| medicine_id | BIGINT | FK → medicine.id |
| quantity | INT | 整数发药数量>0 |
| unit_price | DECIMAL(12,2) | 开立时历史单价≥0 |
| instructions | VARCHAR(255) | 用法说明，后续应用校验非空白 |
| created_at | DATETIME | 创建时间 |

UK(prescription_id,line_no)；medicine_id建索引。明细不存可计算的小计和总计；数量与药品单位一致。

### inventory_movement 库存流水

| 字段 | 类型 | 约束或含义 |
| --- | --- | --- |
| id | BIGINT | PK自增 |
| business_key | VARCHAR(64) | UK，每次业务操作幂等键 |
| medicine_id | BIGINT | FK → medicine_inventory.medicine_id |
| change_quantity | INT | 变动非0；入库正、出库负 |
| balance_after | INT | 此次变动后历史余额≥0 |
| reason | VARCHAR(128) | 出入库原因 |
| reference_no | VARCHAR(64) | 可空，单据追踪号，不冒充强FK |
| created_at | DATETIME | 发生时间 |

库存与流水写入须在同一事务内完成，数据库CHECK不能跨行核对流水余额与当前库存的一致性。流水历史余额是快照事实，不是额外一份当前库存。应用应追加流水，不修改或删除历史流水。

### schema_migration 技术记录

version VARCHAR(32) PK；checksum CHAR(64) NOT NULL；status VARCHAR(16)仅APPLYING/APPLIED/FAILED；completed_steps INT NOT NULL默认0；applied_at DATETIME可空。记录增量版本、SHA-256和执行进度，不授予应用账号修改权限。

## 4. 事务设计为后续业务预留

号源扣减示例，实际代码还需校验排班及业务状态，并检查影响行数：

~~~sql
UPDATE doctor_schedule
SET remaining_capacity=remaining_capacity-1, version=version+1
WHERE id=? AND status='OPEN' AND remaining_capacity>0;
~~~

库存扣减示例：

~~~sql
UPDATE medicine_inventory
SET stock_quantity=stock_quantity-?, version=version+1
WHERE medicine_id=? AND stock_quantity>=?;
~~~

后续挂号Service将号源扣减与挂号插入置于同一个事务；处方Service将处方、明细、库存扣减与流水置于一个事务，任一步失败全部回滚。本次只落实数据库基础与约束测试，尚未实现挂号、处方接口或并发压测。

取消挂号需先在事务内将有效状态改为CANCELLED，仅首次成功转移状态时释放一次号源。处方重试通过处方挂号唯一键和流水幂等键约束，避免重复出库。业务状态机仍需应用层实现。

## 5. 执行方式与重复执行

增量SQL：[V002__medical_business_schema.sql](../sql/migrations/V002__medical_business_schema.sql)。

已有本机加密连接配置及已核验备份后，双击项目根目录“更新数据库结构.cmd”，在可见终端输入管理员账号与口令。口令只通过进程标准输入传给Java，不写入命令参数、日志或配置。

迁移工具固定目标为本机medical_system，获取迁移互斥锁；执行前逐条比较原始四张表快照，遇到不匹配停止；拒绝未知表布局。工具记录迁移状态、校验和、已完成DDL步数，同版本已成功时跳过DDL，并核对结构和数据；未完成版本不盲目重试，须人工定位后续修复。

MySQL DDL不可作为整体事务回滚。执行中断时不自动DROP新表或撤销旧表新增字段，避免误删后续数据。需要恢复时先核查失败步数与当前状态，优先增量修复；完整恢复只针对本项目库且必须明确审核。

脚本原文用于审阅或在全新01结构上由管理员一次执行，不可直接反复运行；推荐使用带迁移记录的工具。工具只新增六表DML权限给已有应用账号，不授予DDL、其他数据库或全局权限。

备份位于 .local/backups，原始数据比对快照、迁移执行结果位于 .local/database-design，均被Git忽略。备份已生成并核对导出完成标志、四张表结构与SHA-256；这不等于已完成灾难恢复演练。
